# 31 — QoL fixes from external feedback (2026-07-29)

## Overview

First round of feedback from an outside user (not the author) who used the editor cold, with no
onboarding. Five points arrived buried in one Discord paragraph; this spec picks them apart into
**three actionable items**, one deferred, and one no-op — plus a documentation fix (item E) found
while investigating.

The value of this batch is that every user-facing item is a **discoverability / convention failure**,
not a missing feature — the capability either exists but is hidden or mismatched, or is gated behind a
modal. That makes this cheap and high-leverage.

### Decisions taken (spec session)

| # | Question | Decision |
|---|---|---|
| Q1 | Collapse/expand position | **Left**, aligned with the existing gutter cell — the toggle box never moves |
| Q2/Q4 | Drop target & landing | **Whole window**, clip lands at the **playhead** (already the modal's behaviour) |
| Q3 | Drop flow | **Open `ImportModal` pre-populated** with the dropped files |
| Q5 | Wheel mapping | ⏸ Moot — item C deferred |
| Q8 | Icons | Effects → `IconFilters`, Animate → `IconEaseInOut`, Presets → `IconPrism` |
| Q9 | The duplicate panel icons | **In scope** |
| Q10 | Batch scope | A, B, D **+ E** (fix stale `CLAUDE.md`) |
| Q11 | Per-effect card icon wiring | **Shared `EFFECT_ICON` map + an `icon` prop on `Accordion`** — one source of truth |
| Q12 | Unsupported-file rejection | **Transient toast** — requires building a small toast system (new component) |

Two decisions carry knock-on scope worth stating plainly:

- **Q3 shrinks item B's import work to nothing.** Because the drop hands off to the existing modal,
  there is no new asset storage, probing, object construction, or lane maths — it reduces to "capture
  the files, open the modal with them staged". The `importPipeline.ts` extraction considered earlier
  is therefore out of scope (see Deferred).
- **Q12 grows item B by one new component.** No toast/notification system exists anywhere in the app
  today, so this batch introduces one. It is the largest new surface here and is specced explicitly
  below (B12-B17) rather than left as an implementation detail. It also enables a better behaviour
  than an empty modal: an all-unsupported drop can toast and **not open the modal at all** (B14).

## Requirements

### A — Timeline collapse/expand toggle must not move

The collapse control and the expand control are currently in **different corners**, so hiding the
timeline strands the user with no visible way back.

- **A1.** The collapse control and the expand control MUST occupy the **same screen position** —
  left-aligned, same fixed-width cell, so collapsing then expanding requires **zero mouse travel**.
  Per Q1 this is satisfied by construction: the collapsed bar's toggle becomes a left-most cell of
  width `GUTTER_WIDTH` (32px), matching the gutter's collapse cell, with the "Timeline" label to its
  right.
- **A2.** The control MUST remain visible and hit-testable in the collapsed state.
- **A3.** The affordance MUST read as a toggle in both states: chevron direction flips
  (down = collapse, up = expand) and the `title` reflects the action ("Collapse timeline" /
  "Expand timeline").
- **A4.** Behaviour, keyboard access, and the collapsed bar's height
  (`COLLAPSED_TIMELINE_HEIGHT` = 32) are otherwise unchanged. This is a placement fix, not a redesign.
- **A5.** No change to state ownership: `timelineCollapsed` stays ephemeral view state in `App`
  (not persisted, not undo) — consistent with `cameraView` and the `LeftRail` open state.

### B — Drop files anywhere in the app to import

Today a first-time user must find "Add media" in the LeftRail, which opens `ImportModal`, and *only
then* can they drop files. The drop target is behind the thing it should replace.

**Drop handling**

- **B1.** Dropping OS files **anywhere in the editor window** MUST open `ImportModal` with those
  files already staged, without the user clicking anything first.
- **B2.** The app MUST show a clear drop-target affordance while a file drag is over the window
  (overlay / outline / "Drop to import"), and clear it on drop, on drag-leave, and on a cancelled
  drag (Esc / drag-out).
- **B3.** The overlay MUST NOT flicker. `dragenter`/`dragleave` fire per descendant element, so this
  needs a drag-depth counter (or a `relatedTarget === null` check, or a single full-window overlay
  that owns the events once a drag begins).
- **B4.** `dragover` MUST call `preventDefault()`, or the browser navigates to / downloads the
  dropped file instead. A file released **outside** the drop target must likewise not navigate the
  page away.
- **B5.** Dropped files MUST flow through the **existing** `ImportModal` staging path
  (`addFiles` → `buildPendingAsset`) — asset storage, duration probe, animated-image probe, waveform
  generation, size warnings, previews, and per-file removal all come along for free. **No second
  import path.**
- **B6.** Clips MUST land at the playhead, as they do today (`insertAtTime={globalTime}`). Multi-file
  drops keep current behaviour: images share a start time and stack on separate lanes; audio/video
  stagger sequentially.
- **B7.** Unsupported file types MUST be rejected **visibly**, via a toast (B12-B17). `addFiles`
  currently filters to `image/*`, `audio/*`, `video/*` and silently discards the rest.
- **B8.** A drop of large files MUST show that work is in progress. `addFiles` currently `await`s
  every `buildPendingAsset` **before** a single `setPending` call, so the modal opens and stays
  **completely empty** until every file has been probed. Rows must appear promptly (a
  `status: 'loading'` row per file, resolving in place) — the pattern already exists for pasted URLs
  and should be reused for files.
- **B9.** If `ImportModal` is **already open**, a drop MUST append to its existing staging list, not
  reset it or open a second modal.
- **B10.** The existing "Add media" → modal path, URL paste, and animated-image import MUST all keep
  working unchanged. This is purely additive.
- **B11.** A file drag MUST NOT trip canvas selection, timeline drags, or the window-level deselect
  handler.

**Toasts (new — required by Q12)**

- **B12.** A minimal toast/notification system MUST be added: a fixed-position container rendered at
  the `App` level, showing short transient messages.
- **B13.** A toast MUST auto-dismiss after a few seconds AND be manually dismissable. Multiple toasts
  MUST stack legibly rather than overlapping, with a sane cap on how many are visible at once.
- **B14.** Dropping files where **none** are supported MUST toast the rejection and **not open the
  modal at all** — an empty modal reads as broken. Where **some** are supported, the modal opens with
  those staged and a toast covers the rejected ones.
- **B15.** The rejection message MUST name the offending file(s), not just say "unsupported".
- **B16.** Toasts MUST NOT block interaction — no modal backdrop, no focus stealing — and MUST NOT
  obscure the timeline, the properties panel, or the transport controls.
- **B17.** The toast API MUST be usable from `ImportModal` (where the rejection is detected) without
  threading a callback through unrelated components. It SHOULD be general enough to reuse for other
  transient messages later, but this batch MUST NOT retrofit existing `alert()`/`window.confirm()`
  call sites (`App.handleImportProject`, the `SIZE_WARN_TOTAL` confirm) — that is separate work.

### D — Retire the ✨ sparkles icon

`IconSparkles` is the universal "AI magic" glyph (Copilot / Gemini / every LLM button). Using it for
video effects makes a fully local, deterministic, no-AI editor look like AI slop.

- **D1.** `IconSparkles` MUST be replaced with **`IconFilters`** on all effects-identity surfaces: the
  LeftRail "Effects" section, the Timeline effects-track gutter, the `PropertiesPanel` effect header
  badge, and the generic `"Effects"` inspector card. `IconFilters` (overlapping circles) reads as
  photographic filtration, not magic.
- **D2.** The same icon MUST be used across all of those, so the feature keeps one identity.
- **D3.** `IconWand` (preset fallback) MUST be replaced with **`IconPrism`** — a magic wand is
  equally AI-coded.
- **D4.** `ContextToolbar`'s "Animate" popover MUST use **`IconEaseInOut`**, not the effects icon —
  entrance/exit animation is a different feature and needs its own identity.
- **D5.** The **15 per-effect parameter cards in `PropertiesPanel` that all show `IconSparkles`** MUST
  each get a distinct, effect-appropriate icon. This is a separate defect the feedback exposed: one
  glyph standing in for 15 different cards carries zero information.
- **D6.** Per Q11, there MUST be **one source of truth** for per-effect icons: an
  `EFFECT_ICON: Record<VideoEffectKind, TablerIcon>` map, consumed by **both** `LeftRail` and
  `PropertiesPanel`. Duplicating icon choices across two files is the condition that produced the
  sparkles dump and MUST NOT be reintroduced.
- **D7.** `Accordion` MUST gain an optional `icon` prop so effect cards can pass their per-kind icon
  explicitly (it currently receives only `title`, with no effect kind in scope).
- **D8.** Non-effect inspector cards (Timing, Position, Points, On Appear, On Exit, Keyframes, Audio,
  Style, Text, Arrow, Focus) MUST be visually unchanged and MUST keep resolving their icons — the
  `SECTION_ICONS` title-keyed lookup stays for them.
- **D9.** Where a per-effect card's title differs from its `EFFECT_LABEL` (`Hue` vs `Hue Shift`,
  `Chromatic` vs `Chromatic Split`), the mismatch MUST be either reconciled or explicitly left alone
  — but MUST NOT be papered over with a second title→kind mapping.
- **D10.** After this item, `grep -rn "IconSparkles\|IconWand" src/` MUST return nothing.
- **D11.** Icon changes MUST NOT alter effect behaviour, IDs, labels, `EFFECT_COLOR`, or which cards
  appear.

- **E5.** Reconcile the **"Done / Planned"** spec list, which stops at 23 and omits specs 16-30

### Item B — the drop path, the two latent bugs, and the new toast layer

Per Q3, the drop hands off to the existing modal, so **no import logic changes**. The drop half is:
a window-level handler in `App` that captures `File[]`, stashes them, and opens the modal; plus a new
prop on `ImportModal` to stage them.

Current contract (`ImportModal.tsx:18-23`), wired at `App.tsx:738-744`:

```ts
type ImportModalProps = {
  onImport: (objects: TimelineObject[]) => void   // = App.addObjects
  onClose: () => void
  insertAtTime?: number                            // = playback.globalTime  → B6 satisfied already
  onAssetsAdded?: (assets: AssetMeta[]) => void    // = dispatch ADD_ASSETS
}
```

The staging entry point to reuse (`ImportModal.tsx:107-122`):

```ts
const addFiles = useCallback(async (files: File[]) => {
  const supported = files.filter(f =>
    f.type.startsWith('image/') || f.type.startsWith('audio/') || f.type.startsWith('video/'))
  if (supported.length === 0) return          // ← B7: silent discard

  const newPending: PendingAsset[] = []
  for (const file of supported) {
    newPending.push(await buildPendingAsset(file))   // ← B8: awaits ALL before any setState
  }
  setPending(prev => [...prev, ...newPending])
}, [])
```

**Two latent bugs**, both of which only *become visible* once a drop can open the modal cold:

- **B7 — silent rejection.** `if (supported.length === 0) return` is tolerable inside an open modal
  (you can see your list didn't grow). On a drop it would open an **empty, silent** modal with no hint
  that `.pdf` isn't supported. Q12's toast plus B14's "don't open the modal at all" resolves this.
- **B8 — no incremental feedback.** The loop `await`s `buildPendingAsset` for every file (which itself
  awaits `getMediaDuration` and `probeAnimatedImage`) and only then calls `setPending` **once**. Drop
  five large videos and the modal is blank for seconds.

  The fix pattern **already exists** in the same file for pasted URLs (`ImportModal.tsx:129-153`):
  insert a row immediately with `status: 'loading'`, then resolve it in place.

  ```ts
  // ImportModal.tsx:129 — addUrl: the incremental pattern to mirror for files
  setPending(prev => [...prev, { id, status: 'loading', name: url, sourceUrl: url }])
  try {
    const file = await fetchAssetFromUrl(url)
    const staged = await buildPendingAsset(file)
    setPending(prev => prev.map(p => (p.id === id ? { ...staged, id, sourceUrl: url } : p)))
  } catch (err) { /* → status: 'error' */ }
  ```

  `PendingAsset` already carries everything needed — **no type changes**:

  ```ts
  // ImportModal.tsx:30-42
  type PendingAsset = {
    id: string
    status: 'ready' | 'loading' | 'error'
    name: string
    file?: File          // only present once the bytes are here
    type?: 'image' | 'audio' | 'video'
    previewUrl?: string
    duration?: number
    sizeWarning?: string
    error?: string
    sourceUrl?: string
    animation?: AnimatedImageInfo
  }
  ```

  `handleImport` already filters to `p.status === 'ready' && p.file`, so loading/error rows are never
  imported — B8 fits the existing model with no downstream risk.

**The toast layer (new).** Nothing comparable exists: current user-facing messaging is
`window.alert` (`App.handleImportProject`, `App.tsx:212-220`) and `window.confirm`
(`SIZE_WARN_TOTAL`, `ImportModal.tsx:244-252`). So B12-B17 add a genuinely new component.

Two shapes to weigh at implementation time:

- **Prop-threaded** (`onNotify?: (msg) => void` on `ImportModal`) — consistent with the existing
  prop-driven style (`onImport`, `onAssetsAdded`), trivially typed, but only serves components `App`
  already passes props to.
- **Module-level store or context** — a `useToasts` hook in `src/hooks/` plus a small module store,
  so any component can push without plumbing. There is precedent for module-level singletons in this
  codebase (`mediaRegistry.ts` is a module-level `Map` written by one hook and read by another), and
  B17 asks for reuse without threading callbacks, which points this way.

Placement matters for B16: the header is top, the timeline bottom, the properties panel right, and the
LeftRail left. Top-centre (under the header) or bottom-centre above the timeline are the least
obstructive; a bottom-right toast risks colliding with the timeline and transport.

**Browser gotchas:**
- `dragover` must `preventDefault()` (B4) or the browser navigates to the file.
- `dragenter`/`dragleave` fire per descendant → counter needed (B3).
- `ImportModal` already registers a **window-level `paste` listener** (`ImportModal.tsx:156-188`).
  A window-level drop handler in `App` plus the modal's own drop handler
  (`ImportModal.tsx:411-413`) means **two** live drop targets when the modal is open — hence B9.
  Simplest resolution: `App`'s handler routes into the same staging call, and the modal's inner drop
  zone keeps working for the already-open case.
- The `Canvas` overlay owns all mouse events, and there's a window-level mousedown deselect handler
  (see `Timeline.tsx:1449` comment) — verify a file drag doesn't trip either (B11).

**On the lane/time path:** no change needed. `addObjects` (`App.tsx:245-258`) already assigns
`maxLane + 1 + i` and selects the last added object, and `insertAtTime={playback.globalTime}` already
gives Q2's playhead landing. Undo comes free — one `ADD_OBJECTS` dispatch per import.

It is consumed by `Accordion`, which **only receives a `title` string** — no effect kind in scope,

  title: string
  ...

Two further wrinkles the implementation must handle:

1. **Card titles are not `EFFECT_LABEL` values.** `EFFECT_LABEL` (`PropertiesPanel.tsx:908-931`, a
   proper `Record<VideoEffectKind, string>` over all 22 kinds) says `'Hue Shift'` and
   `'Chromatic Split'`, while the cards are titled `Hue` and `Chromatic`. So a title→kind lookup
   cannot be derived from `EFFECT_LABEL` — hence D9, and hence passing the icon explicitly rather than
   inferring it from the title.
2. **Only 15 of 22 kinds have a parameter card** — kinds with nothing to tune (grayscale, sepia,
   invert, grain, contrast, bleach, pixelate) have no entry. A full `Record<VideoEffectKind, …>` is
   still the right shape (exhaustive, type-checked), it just won't all be consumed by cards; `LeftRail`
   uses the rest.

`LeftRail` already holds a distinct icon per effect in its creation list (`LeftRail.tsx:133-160`):
`IconContrast`, `IconDroplet`, `IconColorSwatch`, `IconVignette`, `IconGrain`, `IconMovie`,
`IconRainbow`, `IconContrast2`, `IconSunHigh`, `IconFlare`, `IconAperture`, `IconGridDots`,
`IconGradienter`, `IconStack2`, `IconCircleHalf2`, `IconArrowsExchange`, `IconColorPicker`,
`IconGridPattern`, `IconDeviceTv`, `IconDeviceTvOld`, `IconCircles`. **That is the vocabulary
`EFFECT_ICON` should capture** — lifting it there and importing it back into `LeftRail` is the D6
change.

Existing pattern to follow (`LeftRail.tsx:17, 31`) — a module-level `Record<…, TablerIcon>` that keeps
React icon imports out of `effectPresets.ts`:

```ts
type TablerIcon = ComponentType<IconProps>
const PRESET_ICON: Record<string, TablerIcon> = { cinematic: IconVideo, ... }
```

**Verified available** in the installed `@tabler/icons-react@^3.44.0` (checked against
`node_modules/@tabler/icons-react/dist/tabler-icons-react.d.ts`): `IconFilters`, `IconEaseInOut`,
`IconPrism` — all present, along with alternates `IconColorFilter`, `IconTransitionRight`,
`IconContrastFilled`, `IconBrightness`, `IconStack`, `IconWaveSine`, `IconBolt` should any need
swapping on sight.

**Collision to avoid:** `IconAdjustments` is already used in `ContextToolbar` (line 10), so it is not
available as the effects icon. `IconFilters` avoids this.

## Deferred / explicitly out of scope

- **Item C — timeline zoom (the scrollwheel point).** Real and accepted in principle, deferred out of
  this batch by decision. For whenever it's picked up, the investigation is worth keeping: zoom
  **already exists** as `Ctrl`/`Cmd`+wheel (`Timeline.tsx:262-284`, spec 16 A2) with cursor-anchoring
  and `deltaMode` normalisation — the real defect is that it has no visible control and no
  `HotkeysModal` entry, so users assume it doesn't exist. The trap: **trackpad pinch arrives as
  `wheel` with `ctrlKey: true`**, so the current mapping is right for trackpads and wrong for mice;
  a naive "plain wheel = zoom" flip breaks trackpad lane-panning, and a device heuristic needs a
  gesture latch or fast flicks intermittently zoom. The listener must stay **native and non-passive**
  (React's `onWheel` is passive, so `preventDefault` is ignored and the browser page-zooms — a
  regression already fixed once). Constants: `MIN/MAX/DEFAULT_PIXELS_PER_SECOND` = 2/400/80,
  `ZOOM_WHEEL_SENSITIVITY` = 0.0012. Also note `pixelsPerSecond` is component-local `useState`, so
  zoom resets on any `Timeline` remount.
- **Extracting `src/lib/importPipeline.ts`.** `App.handleAddExistingAsset` (`App.tsx:264-290`)
  duplicates the asset→`TimelineObject` construction in `ImportModal.handleImport` — the
  animated-image branch, the 5s still default, `sourceIn`/`sourceOut` seeding, the full-frame
  `x:0,y:0,w:1,h:1` pose, and the waveform call all exist twice. Worth fixing, but Q3's modal
  hand-off means item B adds **no third copy**, so this is pre-existing debt rather than a blocker.
- **Migrating existing `alert()` / `confirm()` call sites to toasts** (B17) — `App.handleImportProject`
  and the `SIZE_WARN_TOTAL` confirm. The new toast system makes this possible; doing it is separate
  work, and the size-warning confirm is a *blocking* prompt that a non-blocking toast cannot replace
  without a behaviour decision.
- **Drop-at-cursor positioning** (clip lands at the dropped time/lane rather than the playhead).
  Needs a `clientY`→lane helper and a lane-occupancy rule — disproportionate to a QoL batch. Revisit
  if playhead landing feels wrong in use.

## Acceptance Criteria

**A — collapse/expand**
1. Collapse the timeline, then expand it, **without moving the mouse** — the toggle is under the
   cursor in both states.
2. The chevron points down when expanded, up when collapsed; `title` matches the action.
3. Collapsed-bar height is unchanged (32px); no layout shift in the surrounding flex column.

**B — drag and drop**
4. Dragging an image/video/audio file from the OS anywhere over the editor shows a drop affordance
   before release.
5. Releasing it opens `ImportModal` with the files **already staged** — no prior click.
6. Clicking Import then places the clip(s) at the playhead; multi-file drops match today's behaviour
   (images share a start time on separate lanes, audio/video stagger).
7. Dropping several large videos shows rows **immediately** in a loading state that resolve in place
   — the modal is never blank-and-silent while probing (B8).
8. Dropping only unsupported files (`.txt`, `.pdf`) shows a toast naming them and **does not open the
   modal** (B14/B15).
9. Dropping a mix shows the modal with the supported files staged **and** a toast for the rejected
   ones (B14).
10. Dropping onto an **already-open** modal appends to the existing list (B9).
11. Dragging in and out without releasing leaves no stuck overlay, and no flicker while moving over
    child elements (B3).
12. A file released outside the drop target does not navigate the page away or download it (B4).
13. A file drag does not deselect the current object or start a canvas/timeline drag (B11).
14. The "Add media" → modal path, URL paste, animated-image import, and size warnings all still work.
15. One undo entry per import; undo removes the added object(s).

**B — toasts**
16. A toast auto-dismisses after a few seconds and can also be dismissed manually.
17. Several toasts at once stack legibly and are capped rather than growing unbounded.
18. Toasts never block clicks, steal focus, or cover the timeline, properties panel, or transport
    controls (B16).

**D — icons**
